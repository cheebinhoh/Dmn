Detailed Description

Backend-neutral remote GATT client contract.

Architecture

The dependency direction between the GATT contract, its BlueZ backend, and the ANCS protocol client is:

* Dmn_GattClient                 backend-neutral GATT interface
*       ^                         (implemented by backends)
*       | implements
* Dmn_BluezGattClient            BlueZ/D-Bus implementation
*
* Dmn_AncsClient --------------> uses Dmn_GattClient
*                                (does not depend on BlueZ)
*

This is the Strategy pattern: ANCS uses the GATT interface while a replaceable backend, such as BlueZ, provides the concrete behavior. It also follows the Dependency Inversion Principle: the ANCS protocol client depends on the GATT abstraction rather than on the BlueZ implementation. Dmn_BluezGattClient can additionally be viewed as an adapter from BlueZ's D-Bus API to the backend-neutral GATT contract.

Dmn_GattClient is the boundary between protocol clients and transport backends. Dmn_BluezGattClient implements that contract using BlueZ and D-Bus. Dmn_AncsClient uses the contract to perform the Apple Notification Center Service (ANCS) protocol, so another GATT backend can be substituted without changing the ANCS client.

The application is responsible for connecting the device before starting ANCS. The ANCS client borrows its Dmn_GattClient and does not connect, pair, or own that backend; the backend must outlive the ANCS client. GATT service and characteristic identifiers are backend-owned opaque values scoped to the current connection and service tree.
